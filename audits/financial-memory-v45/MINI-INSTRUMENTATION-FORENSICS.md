## Notebook query semantics and observed exposure

The shared tool advertises: “Optional literal search text; omit to read all current authorized entries.” Its actual implementation uses one casefolded **whole-query substring** against each fact's text or ID; it is not AND-token, fuzzy, semantic or multilingual search. For Super OT-off49e459..., stored current text is `ROE phải trên 20%`, ID `roe-active`, revision2; query `ROE condition ACB STB VPB HDB TPB` matches neither, so returning facts=[] is consistent with the published literal-query semantics. This is a caller retrieval mismatch with a potentially weak ergonomic design, not evidence that the backend dropped the fact. Omission/empty query and query `ROE` work. Future descriptions should explicitly state whole-substring semantics and distinguish “no matching facts” from “no saved facts”; changing retrieval semantics would require a new version.

Across8 update/revoke episodes,6 reach fresh sessionB. Of those,4 expose current revision2 via actual shared-read trace IDs in B request captures (SuperDSH, DeepSeekOT-on/OpenCode/DSH); SuperOT-on has no B shared read but verifies one native stored active entry, requiring independent actual native-context review; SuperOT-off has one B read with empty facts as above. DeepSeekOT-off and SuperOpenCode DNF before B. Thus controller shared-state existence alone cannot establish model exposure or memory causality. Exact per-episode observations are in `MINI-UPDATE-RULE-EXPOSURE.json`. Native persistence and shared retrieval are distinct paths; absence of common reads is not failure when native integration legitimately exposes the authorized fact.

A sensible projection that the published production interface supports must not automatically be reported as poor financial reasoning, wrong tool name, fabricated evidence, or real production query invalidity. Preserve the failed call and its cost, but classify its origin accurately. No snapshot matcher was changed here.
